# Re-deriving Before Asserting

## Overview

There are two ways a claim can feel true. **Recognition** — "this sounds like things I've seen" — and **re-derivation** — reconstructing it from ground truth. Fluency and accuracy are generated by the same process and feel identical from inside; no amount of confidence distinguishes them. Only touching ground truth does.

## Procedure

1. **Name the ground-truth source** of every load-bearing claim: a file, a command output, a computation, an observation. Can't name one? It's a guess — label it as one, or don't assert it.

2. **Touch the source before asserting.** The bar: could you show the evidence if asked? "I'm confident" is not evidence.

3. **Check the version.** "The default is X" is meaningless without "in version Y". Read the lockfile/pin, then the installed source — not your memory of the library.

4. **Re-derive by a different method** than the one that produced the claim: confirm a config by reading the code that *consumes* it; compute a total a second way. A check sharing the original's method shares its blind spots.

5. **Treat summaries as claims, not ground truth.** Status footers, `SUCCESS` banners, dashboards, and aggregate metrics *summarize* — and summaries drop things. Before reporting a log or dataset as clean, ask: *what would a disconfirming line look like?* — then search for that specifically, including negative phrasing (`halted`, `excluded`, `unresponsive`, `skipped`, `remains on`), not just `error|fail|warn`. Absence of ERROR is not presence of health.

6. **When the user "remembers" a fact and asks you to confirm:** confirming is asserting. Check anyway. "You're right" without evidence is the same failure as any other unverified claim.

## Quick reference — highest-yield checks (usually one command)

| Claim type | Ground truth |
|---|---|
| Version / default / flag | lockfile + installed source (`grep node_modules/...`) |
| "No override configured" | grep the app source for the setting |
| "Log is clean / deploy healthy" | anomaly search beyond error keywords; inverse-grep the healthy patterns |
| Count / total | recompute by a second method |
| Path / name / symbol exists | `ls` / grep it |

## Example

"pool-lib defaults its timeout to 30s — just confirm." Sixty seconds: `package.json` pins `^3.2.0`; `node_modules/pool-lib/lib/defaults.js` says `10000` — changed in v3.0.0. The confident confirmation you were about to give was wrong, and nothing internal flagged it. Only the grep did.

## Rationalizations

| Excuse | Reality |
|---|---|
| "I'm sure — I've seen this a hundred times" | You've seen *a version* of it. Check the pinned one |
| "The user just needs a quick confirm" | A fast wrong answer in an incident doc is the slowest outcome |
| "The status line says SUCCESS" | The status line is the system summarizing itself |
| "I grepped for errors, nothing" | Disconfirming lines often carry no error keywords |
| "No time to check" | The check is one command; the correction cycle is not |
