# Skill: qa-handoff

Hand the work off to Fede for human QA. **Rigid skill — follow every step in order.**

## When to trigger

- The work-on-issue procedure has finished implementing the issue's plan.
- User says "ready for QA", "hand it off", "done", or invokes `/qa-handoff`.
- Implementation has stopped changing files and the next action is "show Fede".

## Pre-flight

You must be inside a worktree at `../portfolio-issue-N/` on branch `feature/issue-N-<slug>`. If `git rev-parse --abbrev-ref HEAD` does not match this pattern, refuse and ask Fede where he is.

Extract `N` from the branch name.

## Procedure

### 1. Local verification — refuse to hand off on failure

Run in the worktree:

```bash
pnpm typecheck
pnpm lint
pnpm build
```

If **any** of these fail:
- Do **not** push, do **not** open a PR.
- Show Fede the failing output in plain language ("typecheck failed at app/foo/bar.tsx line 42 — variable `x` is unused").
- Stop and fix in this same worktree, then retry the skill.

### 2. Stage + commit

If there are unstaged or untracked changes that should ship:

```bash
git add -A
```

Commit with Conventional Commits format. Read the issue title to pick the right `type` and `scope`:

```bash
git commit -m "<type>(<scope>): <summary> (#${N})"
```

Examples:
- `feat(case-study): per-project scoped chat widget (#24)`
- `fix(api): handle empty result from search (#12)`

### 3. Push the branch

```bash
git push -u origin "feature/issue-${N}-${SLUG}"
```

### 4. Open the PR

Extract the issue's QA checklist from its body and inline it into the PR body. Use this exact template:

```bash
PR_BODY=$(cat <<EOF
Closes #${N}

## Summary
- <1–3 bullets: what changed and why>

## Screenshots / Recordings
<for UI work — paste later if relevant; remove section if N/A>

## QA Checklist (copied from the issue)
$(gh issue view "${N}" --json body --jq '.body' | awk '/## QA Checklist/,/## Done When/' | sed '$d')
- [ ] \`pnpm typecheck\` passes
- [ ] \`pnpm lint\` passes
- [ ] \`pnpm build\` passes

## Notes for Reviewer
<anything Fede needs to know — env-var changes, follow-ups, deferred items>

---
🤖 Generated by Claude Code — issue-driven workflow per [CONTRIBUTING.md](../CONTRIBUTING.md)
EOF
)

gh pr create \
  --base main \
  --head "feature/issue-${N}-${SLUG}" \
  --title "<type>(<scope>): <summary> (#${N})" \
  --body "$PR_BODY"
```

Capture the resulting PR URL.

### 5. Flip the issue label

```bash
gh issue edit "$N" --remove-label "status:in-progress" --add-label "status:qa-pending"
gh issue comment "$N" --body "✅ **READY FOR QA**

**PR**: ${PR_URL}

**Run the QA checklist below in chat and reply with approval or feedback.**"
```

### 6. Emit the FEDE QA block in chat

This is the most important step. Translate the issue's "QA Checklist" from technical phrasing into plain-language action+expectation pairs. **Fede does not read code.** Each step is something he physically does, with the expected result.

Use this literal format. Fill the blanks; keep the box-drawing characters:

```
── FEDE QA — Issue #N ──────────────────────────
Worktree:  ../portfolio-issue-N
Branch:    feature/issue-N-<slug>
PR:        <full PR URL>

Run this in a fresh terminal:
  cd ../portfolio-issue-N
  pnpm dev
  open http://localhost:3000/<path-most-relevant-to-this-issue>

Then check, in order:

1. <plain-language action>
   → Expected: <what you should see / what should happen>

2. <plain-language action>
   → Expected: <...>

3. <plain-language action>
   → Expected: <...>

Reply `approved` when all checks pass — I'll merge, clean up the worktree,
update the labels, and tell you what's newly unblocked.

Reply with what's off if something fails — I'll fix in this same worktree
and re-emit the QA block.
────────────────────────────────────────────────
```

### Rules for writing the QA steps

- **No file paths**, no component names, no code in the steps. Fede shouldn't need to know what `SectionAI.tsx` is.
- **One action per step.** "Scroll to the AI section. Expected: the cards appear with a slight fade-in."
- **State the URL** for any new route the issue introduces.
- **If the issue involves multiple devices** (mobile / desktop), include a "Repeat steps 1-3 in mobile DevTools (iPhone 14)" final step.
- **If the issue mentions `prefers-reduced-motion`**, include a step: "Enable Reduce Motion in macOS System Settings → Accessibility. Refresh. Expected: animations are off but the final state is visible."
- **If the issue ships an API route**, include a curl step Fede can paste literally.

### 7. Stop and wait

Do not proceed past the QA block. Wait for Fede's reply:
- `approved` (or `lgtm`, `ship it`) → trigger the `ship-it` skill.
- Any specific feedback → fix in the same worktree, then re-run this skill from step 1.

## What this skill does NOT do

- Does not merge anything.
- Does not delete the branch.
- Does not flip `status:qa-pending` → `status:completed` (that's `ship-it`).
- Does not cascade labels to dependents.
- Does not remove the worktree.

## Failure modes

- **CI not yet wired**: if `gh pr checks` returns "no checks", that's fine for now — the CI workflow is `.github/workflows/ci.yml`. Mention to Fede that checks are pending and will appear within ~30s.
- **Pushed but PR create fails**: the branch is still pushed. Re-run `gh pr create` directly; don't re-do steps 1-3.
- **Issue label flip fails**: PR is still open and valid. Tell Fede; he can flip manually with `gh issue edit`.
